# Dead Code Analysis

Generated by a real cross-file usage scanner (checks both named imports and `import * as alias` + `alias.member` usage patterns), then hand-verified against the actual codebase for every item where "unused" could plausibly mean something other than "safe to delete." Raw scan: 363 named exports, 107 with no in-repo importer. After investigation, those 107 fall into four real categories — and two of them led to fixing genuine live bugs (see below).

## Category A — Confirmed dead, remove now (migration debt, purpose served)

| Item | File | Why it's safe to remove |
|---|---|---|
| `storageGet()`, `storageSet()` | `db/repository.js` | Phase 3's intentional "throw loudly if anything still calls the old blob API" safety net. Grepped: zero callers anywhere, including in comments except one explanatory note. Migration is confirmed complete — these have served their purpose. |
| Namespace re-exports (`jobsRepo`, `blockersRepo`, `notesRepo`, `checklistRepo`, `blueprintsRepo`, `activityRepo`) | `db/repository.js` | Nobody imports `{ jobsRepo }` *from `repository.js`* — every consumer imports each repo directly from its own file (`db/jobsRepo.js`, etc.), a pattern that emerged from Phase 8/9 onward. The re-export is vestigial from early Phase 3 design. |

## Category B — Investigation revealed real bugs, not dead code (fixed this phase)

| Item | What investigating "why is this unused" actually found |
|---|---|
| `deleteJob` (jobsRepo) | `events.js`'s `delete-job` handler never called it — it only removed the job from local browser state and called `persistJobs()`, which had no deletion-detection logic for jobs at all. **The job was never actually deleted from the database.** Fixed by adding the missing deletion-detection block to `persistJobs()`, mirroring the pattern `persistBlockers()` already had. |
| `setSelectedBlueprintFile`/`getSelectedBlueprintFile` (state/store.js) | Built correctly in Phase 1 specifically because ES module named imports are read-only to importers — but later phases' blueprint UI code bypassed them and directly reassigned the imported `selectedBlueprintFile` binding instead. **This throws `TypeError: Assignment to constant variable` at runtime**, breaking blueprint file selection entirely. Confirmed by direct reproduction, then fixed by routing all four call sites through the proper setter/getter. |
| *(discovered while fixing the above)* `persistBlockers()`'s deletion path | Had the identical flaw as the jobs bug: an early `if(!dirty.length) return true` skipped the deletion-detection loop whenever a delete was the *only* pending change — the common case for a single blocker deletion. Fixed alongside the jobs fix. |

All three are covered by new permanent regression tests: `tests/persist-deletion.test.mjs`, `tests/blocker-deletion.test.mjs`, `tests/blueprint-file-select.test.mjs` — 13 assertions, all passing.

## Category C — Legitimate unbuilt-UI public API, keep

| Item | File | Why it's not dead |
|---|---|---|
| `onAuthStateChange`, `refreshSession`, `updatePassword` | `auth/authService.js` | Necessary Supabase Auth surface for features not yet built: a session-change listener, and the password-reset landing page (the *request* half — `requestPasswordReset()` — is wired into `loginView.js`; the *confirm new password* half has no UI yet). Keep — needed the moment `AUTH_ENABLED` flips on and that page gets built. |
| `getProfile`, `updateProfile`, `setCachedProfile`, `createProfileForUser` (partial) | `auth/profileService.js` | Public profile-management API with no admin UI consuming it yet (`canManageUsers()` exists in permissions.js with the same status — built for a user-management screen that doesn't exist yet). |
| `getVersion`, `diffVersions`, `listComponents` (standalone), `getAuthHeaders`, `supabaseHeaders` | various `db/` | Genuine repository/client API surface, either used only internally within their own file (correctly, no export needed externally) or awaiting a UI that composes them (e.g. `diffVersions` is used internally by `compareVersions`, which *is* wired to the UI). |

## Category D — Exported but only used within their own defining file

`stageForLocation`, `validateComponents`, `normalizeSpecTree`, `checklistRowsToMap`, and about a dozen others follow this pattern: actively called, just never across a module boundary. Not a bug, not dead — a minor style note (could be un-exported for a marginally clearer public/private API boundary), listed here for completeness rather than urgency.

## Recommended action
Remove Category A now (two items, ~15 lines). Category B is already fixed. Categories C and D: no action — removing them would delete legitimate, load-bearing code.
